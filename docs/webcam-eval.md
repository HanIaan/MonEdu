# 실제 웹캠 현장 평가 체계

Phase 2의 정확도 수치는 COCO·Wikimedia **사진**과 E2E용 **캔버스 카메라**(사진 재생)로 측정한 값입니다.
이 문서는 실제 사람이 실제 웹캠 앞에서 정해진 동작을 하며 **출시된 엔진 그대로** 평가하는 절차입니다.
앱 코드는 바꾸지 않습니다. 평가 도구는 `tests/e2e/specs/webcam.eval.spec.ts`(opt-in)와
`tests/e2e/scripts/webcam-eval-summary.mjs`입니다.

## 1. 개인정보 원칙 (도구가 강제하는 것)
| 항목 | 처리 |
|---|---|
| 영상·프레임·얼굴 이미지 | **어디에도 저장·전송하지 않음.** 도구는 `page.screenshot()`을 호출하지 않고, 프로젝트 설정에서 trace/screenshot/video를 끔 |
| 서버로 가는 것 | 평소 서비스와 동일한 상태 이벤트와 heartbeat뿐(숫자·상태값). 영상 없음 |
| 저장되는 것 | 이 컴퓨터의 `tests/e2e/test-results/webcam-eval-*.json`(gitignore 대상) 한 개. 내용은 상태 변화 시각, 프레임별 모델 점수(얼굴·어깨·사람·휴대폰 점수, 추론 ms), 구간 이름뿐 |
| 동의 | 카메라 앞의 사람이 **직접** 앱의 동의 체크 → ‘학습 시작’ → 브라우저 카메라 권한 ‘허용’을 누름. 도구는 권한을 자동 부여하지 않음. 동의하지 않으면 창을 닫으면 끝 |
| 제3자 | 화면에 다른 사람이 들어오지 않는 곳에서 진행. 다른 사람을 평가하려면 그 사람의 동의를 먼저 받을 것 |
| 삭제 | 결과 파일을 지우면 끝(서버에는 일반 학습 기록만 남음. 평가용 계정 student3 사용 권장) |

## 2. 준비
1. 백엔드(8080)와 프론트엔드(3000)를 실행합니다. 프론트엔드는 진단 훅(`window.__smDiag`)이 필요하므로
   개발 서버(`npm run dev`) 또는 `NEXT_PUBLIC_E2E_DIAGNOSTICS=1`로 빌드한 프로덕션 서버여야 합니다.
2. macOS 시스템 설정 ▸ 개인정보 보호 및 보안 ▸ 카메라에서 이 도구를 실행하는 터미널 앱(또는 Chrome)을 허용합니다.
3. 조건을 기록할 메모를 정합니다. 예: `"낮 창가 역광, 내장 FaceTime HD, 60cm, 안경"`.

## 3. 실행
```bash
cd tests/e2e
# 실제 웹캠 (Chromium 창이 뜸 → 화면 왼쪽 아래 안내를 따라 하기, 약 10분)
WEBCAM_EVAL=1 WEBCAM_EVAL_NOTE="밝은 실내, 내장 카메라, 60cm" npx playwright test --project webcam-eval
# 설치된 Google Chrome으로:  WEBCAM_EVAL_CHANNEL=chrome 추가
# 여러 번 실행한 뒤 합산 표:
node scripts/webcam-eval-summary.mjs
```
도구가 하는 일은 다음과 같습니다. 단계가 바뀔 때마다 "삐" 소리가 나므로 화면을 보지 않아도 따라 할 수 있습니다.
1. 로그인합니다.
2. 동의와 시작을 기다립니다(최대 5분).
3. 아래 프로토콜을 진행합니다. 단계 사이에 8초 준비 시간이 있습니다.
4. 학습을 종료하고 결과를 저장합니다.

도구 자체 점검(카메라 없이 사진으로 배관만 확인. **현장 결과 아님**):
```bash
WEBCAM_EVAL=1 WEBCAM_EVAL_FAKE=1 npx playwright test --project webcam-eval
```

## 4. 프로토콜과 기대 결과
기준 시간은 `docs/contracts/state-machine.md` §3에서 왔습니다(착석 확인 15초, 휴대폰 20초, 자리비움 30초, 히스테리시스 3초).

| # | 구간 | 하는 일 | 길이 | 기대 상태 | 통과 기준 |
|---|---|---|---|---|---|
| 1 | 정면 착석 | 정면에 앉아 화면 보기 | 75초 | 집중 추정 | 35초 안에 도달하고, 그 뒤 90% 이상 유지 |
| 2 | 필기 | 고개 숙여 노트에 쓰기, 어깨는 화면 안 | 75초 | 집중 추정 | 20초 안에 도달·유지 90% 이상, **자리비움 0초** |
| 3 | 독서 | 책 읽기(들거나 내려다보기) | 75초 | 집중 추정 | 2번과 같음 |
| 4 | 휴대폰 사용 | 휴대폰을 들고 사용, 카메라에 보이게 | 60초 | 비집중 의심 | 35초 안에 도달(엔진 기준 20초 + 히스테리시스) |
| 5 | 휴대폰 내려놓기 | 정면에 앉기 | 40초 | 집중 추정 | 25초 안에 도달 |
| 6 | 자리 비움 | 화면 밖으로 나가기 | 60초 | 자리비움 | 45초 안에 도달(30초 + 걸어 나가는 시간) |
| 7 | 복귀 | 돌아와 앉기(삐 2번) | 40초 | 집중 추정 | 25초 안에 도달 |
| 8 | 엎드린 자세 | 팔을 베고 엎드리기 | 60초 | **관찰만** | 판정 규칙이 없음. 실제로 어떤 상태가 되는지 기록 |
| 9 | 정면 착석 | 마무리 | 30초 | 집중 추정 | 25초 안에 도달 |

엎드린 자세를 미리 예상하면 이렇습니다. 사진 측정(`frontend/bench/vision/RESULTS.md` §C)에서 엎드린 자세는 필기와 같은 신호가 나와
`집중 추정`, `측정 불가`, `자리비움` 중 어느 것도 될 수 있습니다. 수면 감지는 출시하지 않았으므로 이 구간은 **현재 한계의 크기를 재는 것**이 목적입니다.

## 5. 결과 해석
결과 파일과 요약 표의 항목은 다음과 같습니다.
| 항목 | 뜻 |
|---|---|
| `reachedAfterSec` | 구간 시작부터 기대 상태가 될 때까지 걸린 시간 |
| `heldShare` | 도달 기준 시간 이후, 기대 상태로 머문 비율 |
| `falseAwaySec` | 공부 중인데 `자리비움`으로 잘못 잡힌 시간(공정성 핵심 지표) |
| `falseDistractionSec` | 휴대폰 없이 `비집중 의심`으로 잘못 잡힌 시간 |
| `evidence.*` | 프레임별 신호 비율. 얼굴 점수 0.6 이상, 어깨 보임, 사람 점수 0.5 이상, 휴대폰 점수 0.5 이상(물체 탐지 프레임 기준). 휴대폰 최고 점수, 추론 p95 |
| `serverTotalsDelta` | 같은 시간 동안 서버 일일 집계 변화(집중·자리비움·측정 불가 초) |

권장하는 조건 조합은 다음과 같습니다. 조건마다 최소 3회 반복하고, 반복 횟수와 실패 횟수를 숨기지 말고 그대로 보고합니다.
| 축 | 수준 |
|---|---|
| 조명 | 밝은 실내 / 어두운 실내(스탠드만) / 창가 역광 |
| 거리·각도 | 노트북 내장(정면 50–70cm) / 외장 카메라 모니터 위(위에서 내려다봄) |
| 사람 | 안경 유무, 머리 모양, 2명 이상(동의 받은 경우) |
| 휴대폰 | 얼굴 앞에 들기 / 책상 아래로 내려 보기 / 책상 위에 놓고 터치 |
| 기기 | 고성능 맥 / 저사양 노트북(측정 시 `infP95Ms`, `lowPower` 확인) |

**통과로 볼 수 있는 기준(제안)**은 다음 네 가지입니다.
- 1·2·3·5·7·9 구간 통과율 ≥ 90%
- 필기·독서의 `falseAwaySec` = 0
- 6번(자리비움) 통과율 ≥ 90%
- 4번(휴대폰)은 조건별 통과율을 그대로 보고(현재 사진 기준 재현율 0.38이라 낮게 나올 수 있음)

## 6. Safari에서 같은 평가
Playwright로는 실제 Safari.app을 조종할 수 없습니다. Safari에서는 위 프로토콜을 사람이 진행하고,
선생님 화면(다른 브라우저의 teacher2)의 학생 타임라인과 학생 화면의 상태 표시를 보고 구간별 상태를 기록합니다.
Safari 개발자 도구 콘솔에서 `__smDiag.snapshot()`을 실행하면 같은 상태와 점수를 볼 수 있습니다(진단 빌드 한정).
자세한 Safari 절차는 `docs/safari-manual-checklist.md`에 있습니다.

## 7. 이 체계의 한계
- 한 사람이 한 번 하는 평가는 표본이 작습니다. 사람·조명·카메라를 바꿔 반복해야 의미가 있습니다.
- 사람이 안내를 늦게 따르면 도달 시간이 늘어납니다. 준비 8초와 넉넉한 통과 기준으로 일부만 흡수합니다.
- 정답 라벨은 "프로토콜상 그 시간에 하라고 한 동작"입니다. 사람이 실제로 다르게 행동한 시간은 구분하지 못합니다.
- 결과 파일에는 영상이 없으므로, 실패 원인을 장면으로 다시 확인할 수 없습니다. 실패 구간의 점수(`evidence`)로만 추정합니다.
